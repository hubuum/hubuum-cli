Install and update CLI binaries¶

Release binaries¶

Successful pushes to main publish rolling binaries in the main-latest release. Version tags such as v0.0.14 publish immutable, versioned GitHub releases.

Each release provides four small, stripped archives and matching SHA-256 files:

  • Linux x86_64 and ARM64 binaries are statically linked with musl.
  • The Apple Silicon macOS binary depends only on Apple-provided system libraries.
  • The Windows x86_64 binary uses the MSVC ABI with a statically linked C runtime; Windows system DLLs remain platform dependencies.

Rolling builds identify their source commit using SemVer build metadata, for example v0.0.14+main.g0123456789ab. Tagged releases use the clean package version. Show the current build identity without logging in, or also query the configured server:

hubuum-cli version
hubuum-cli version --server
hubuum-cli version --output json

The same version commands are available in the REPL. The server version comes from the server's unauthenticated OpenAPI metadata.

Updating in place¶

Starting with v0.0.13, check for or install the latest stable GitHub release:

hubuum-cli self-update --check
hubuum-cli self-update
hubuum-cli self-update --check --output json

These commands also work in the REPL and require no Hubuum login. --check reads release metadata without downloading an archive or changing the executable. Installation verifies the archive against its published SHA-256 file before replacing the running executable on disk. Restart the CLI or REPL afterward; the current process continues running its original version.

The updater probes the installation directory for write access before downloading the archive. Permission errors identify the target path and suggest using the package manager or contacting an administrator. --check needs no write access. For a package-managed installation, use its package manager. Supported targets match the four release platforms above; Linux GNU builds receive the corresponding static musl binary. Other targets must use their original installation method. The updater uses the self_update crate.

Only strictly newer stable versions are installed. Prereleases and main-latest are never destinations; a rolling build waits for a stable release with a higher version, ignoring its build metadata. GitHub requests optionally use GH_TOKEN or GITHUB_TOKEN (in that order) for API rate limits. Hubuum credentials are not used. JSON output reports status (up_to_date, update_available, or updated), both versions, the executable path, target, and restart_required.

Startup checks and managed installations¶

Self-update is enabled by default; automatic checks are off. These settings can be placed in the CLI's TOML configuration:

[self_update]
enabled = true
check_on_startup = false

Set check_on_startup = true to check once when the interactive shell starts. The check reads GitHub release metadata and prints a notice only when a newer stable release is available. It never downloads or installs an update. Requests use a three-second timeout; unavailable networks and other check failures do not interrupt startup or print warnings. Debug logging records failures. One-shot commands, scripts, help, and version output do not perform startup checks.

Administrators packaging the CLI can set enabled = false in the system config to suppress startup checks and reject both self-update and self-update --check before any network access. The error directs users to their package manager or administrator. This setting takes precedence over check_on_startup.

Use hubuum-cli config paths to locate the system and user config files. The system path is /etc/hubuum_cli/config.toml on Linux, /Library/Application Support/hubuum_cli/config.toml on macOS, and C:\ProgramData\hubuum_cli\config.toml on Windows. Normal configuration precedence applies: user configuration, environment variables, and an explicit --config file can override system defaults. These are local settings and are not exported to or imported from server-stored user preferences.

Both keys support config show, config set, and config unset without a Hubuum server connection, even when automatic server preference storage is enabled:

hubuum-cli config set --key self_update.check_on_startup --value true
hubuum-cli config set --key self_update.enabled --value false

The corresponding environment variables are HUBUUM_CLI__SELF_UPDATE__ENABLED and HUBUUM_CLI__SELF_UPDATE__CHECK_ON_STARTUP, accepting true or false.
