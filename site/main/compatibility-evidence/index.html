Compatibility evidence and history¶

Hubuum CLI, hubuum_client, and the Hubuum server are versioned independently. Each CLI release pins a hubuum_client version; that client library declares and reproducibly tests its Hubuum server target. CLI v0.0.18 uses hubuum_client 0.16.0, which targets Hubuum server v0.0.20. The CLI inherits this compatibility target from its client dependency and runs its own integration checks against the same pinned server. Command availability against other server versions is not guaranteed.

Unreleased: persistent password sessions¶

The session-persistence fix pins SDK commit ad4bde4fa88a34fc2373ef232bd6cd64d237cea7 from SDK PR #124. This temporarily replaces the published 0.16.0 dependency with an immutable Git source providing the storage interface. It includes the SDK main-branch additions already merged before that fix. The server v0.0.20 target, OpenAPI routes, and blocking-only feature selection remain unchanged. The SDK keeps Rust 1.88; the CLI declares no MSRV and uses Rust 1.89's standard filesystem locking API.

The CLI stores rotating sessions in an identity-scoped cache and coordinates refresh through a stable lock file and atomic durable replacement. Passwords are not stored. Existing legacy-token migration and explicit PAT/service-token files remain supported. The SDK validates stored server/client bindings and invalidates consumed refresh credentials before exchange.

File storage remains the default. Runtime opt-in keychain storage adds keyring-core 1.0.1 and the target-specific Apple Keychain 1.0.2 and D-Bus Secret Service 1.0.1 stores, using Rust cryptography and vendored libdbus on Linux. The credential pair is stored directly in the native store, with the same exclusive process lock. File-to-keychain migration preserves unrelated accounts and stops on storage failure. Existing Unix cache and lock-file permissions are repaired before use. No password or plaintext fallback is stored by the keychain backend. Selecting none instead uses the SDK's existing in-memory login API and skips both persistent stores and legacy-token reuse. It introduces no dependencies or server API changes. Regressions verify fresh logins, preservation of existing caches, absence of session files, and explicit token-file precedence.

Verification uses the immutable server image ghcr.io/hubuum/hubuum-server@sha256:eaf59f8a4b4793030a78bc1637a8e2b9fad2f810b8621ff9a874dca534b9a23a. The live CLI driver covers password login, restart without credentials, and two concurrent processes refreshing a saved session, alongside the complete existing integration and restore/recovery suite. The companion SDK's complete pinned library/consumer suite also verifies client recreation after real access-token expiry. Workspace regressions cover independent processes, identity isolation, cache permissions, redaction, malformed caches, and preservation of other accounts.

The keychain follow-up passed 830 workspace tests plus two native Linux tests in an isolated D-Bus/GNOME Keyring container: credential persistence across recreated stores, and four CLI processes migrating a file session, resuming without a password, and coordinating exactly one refresh. The latter verifies the consumed refresh credential is absent from the native store before exchange and that the plaintext session entry was removed. macOS native validation is included in CI; it was not run on this Linux workstation. Strict Clippy, formatting, Markdown, wrapper and CI-policy checks, dependency audit, and a musl compile check passed.

The memory-only follow-up passed 832 workspace tests, strict Clippy, formatting, Markdown lint, and CI-policy checks. The full pinned live suite passed again, including fresh memory-only logins both beside an existing cache and in an empty data directory; existing credentials remained unchanged and no session files were created. The preceding keychain commit also passed native macOS and Linux CI validation.

Concurrent cache-miss login coverage forces two clients to finish their initial cache checks before either receives a password, for both empty and expired caches. A stable login lock coordinates the subsequent recheck and login/save; the regression requires exactly one login and successful requests from both clients after authentication completes. Separate CLI subprocesses also share one cold-start login. The pinned live driver covers concurrent empty/expired cache recovery alongside refresh coordination and memory-only authentication. All 833 workspace tests passed, as did strict Clippy, formatting, Markdown lint, 18 CI-policy tests, and the complete pinned live suite with three restore cycles. This changes no dependencies, server API, or MSRV requirements.

CLI v0.0.18: client v0.16.0¶

Verified on 2026-10-22 using the published crates.io hubuum_client 0.16.0, with registry checksum 452c0ac2946af679a220a92eef8c804b3927521428dfb0cb5c1bc08b042312b4. The final lockfile uses the registry package, without a local path override. The SDK release commit is 74349baca65a957d302ade3319bc4d599ec7369f.

The complete CLI live suite used the released server v0.0.20 image: ghcr.io/hubuum/hubuum-server@sha256:eaf59f8a4b4793030a78bc1637a8e2b9fad2f810b8621ff9a874dca534b9a23a. Its source revision is 3bede6e5b815585f3ac5372cc829734b2ae14a68. Password login and provider discovery use the new /api/v1/auth contract. Interactive sessions rotate in memory; newly acquired credentials are not written to the legacy token cache. Explicit PAT files remain supported.

All 819 workspace tests passed, together with strict workspace/all-target Clippy, rustfmt, CI-policy regressions, extension wrapper tests, extension schema validation, and Markdown lint. The dependency refresh includes the published SDK and ICU 2.4; the vulnerability audit passed. cargo update reports no further compatible updates. Upstream exact requirements retain psm 0.1.24 through pest and generic-array 0.14.7 through crypto-common.

The pinned live driver passed collection integrations, delegated permissions, structured search and streaming, credential approvals, schema evolution, query usage, and all three format 10 backup/restore cycles. It also verifies that password login can read administrator configuration without printing the password or persisting the session, and that second-generation recovery preserves mutations and prior deletions.

Breaking upgrade: upgrade the server API, workers, and restore executor together during the offline migration, retain a pre-upgrade PostgreSQL snapshot and binaries, and sign in again. Each new CLI process requires credentials unless using an explicit PAT file; use the REPL to reuse an interactive session. Older servers cannot restore format 10 output.

An authorized read-only Hosts query on 2026-10-19 returned two rows with three client API calls and three HTTP attempts, all status 200, inside a single JSON response with empty stderr. All 813 workspace tests passed, together with Clippy, rustfmt, Markdown lint, wrapper tests, extension schema validation, and CI-policy tests. The disposable-server integration suite passed against that pinned image, including all three format 9 restore cycles and the supported command/streaming surfaces. A fresh audit found no vulnerable dependencies in the 424-package lockfile.

CLI v0.0.16: client v0.15.1¶

CLI v0.0.16 pins the published hubuum_client 0.15.1 for its versioned tracing contract. The server target remains v0.0.19, with immutable image ghcr.io/hubuum/hubuum-server@sha256:6fbe91693356b8885e6b1115cea4417dbf80747ba4af3eb0a15b855ffff47225. The 240-operation OpenAPI contract and 111 wire-model mappings are unchanged. The CLI still enables only the client's blocking feature; the client retains Rust 1.88 as its MSRV, and the CLI declares no MSRV. tracing 0.1 is now a direct CLI dependency, using the version already in its lockfile.

On 2026-10-19, all 808 workspace tests passed using the crates.io package with its registry checksum locked. Clippy, formatting, tracked Markdown lint, wrapper tests, extension JSON Schema validation, and CI-policy tests passed. Diagnostics tests verify real HTTP responses, failure statuses, span ancestry, cancellation boundaries, command isolation, and clean JSON/redirection. An authorized read-only live query also confirmed four client calls and four native HTTP attempts. Verification used Rust 1.98.0. A refreshed advisory audit found no vulnerable dependencies in the final 424-package lockfile.

The complete disposable-server integration suite passed against the pinned image with the registry client, including delegated integrations, query usage, structured streaming, graph limits, credential approvals, schema evolution, and all three format 9 restore cycles. Recovery retained object and query-usage revisions, JSON nulls, and earlier deletions; old tokens were invalidated.

Command diagnostics collect the client's version 1 tracing contract beneath one root per command, with separate API-call and HTTP-attempt counts. Startup and detached background activity are excluded. Reports use stderr so structured output and file redirection keep their existing formats.

Breaking for extension authors: debug and --debug are reserved host options. Rename any conflicting extension option before upgrading; executable extensions do not receive this host flag.

CLI v0.0.14: client v0.14.1¶

CLI v0.0.14 pins the published hubuum_client 0.14.1, which targets Hubuum server v0.0.18. The client reconciles all 235 operations and 338 schemas, with 88 wire-model mappings. CLI integrations use the same immutable released server image recorded in Cargo.toml. The client enables only its blocking feature and retains Rust 1.88 as its MSRV; the CLI declares no MSRV and is verified with Rust 1.99. The Rust client's public API remains compatible with 0.14.0.

Verification on 2026-10-06 used the published crates.io client and released server image ghcr.io/hubuum/hubuum-server@sha256:5b54248f19171200dfa497174d385a48f90666a415cb31732797043d5e182fc4, from server commit 35fcf6696d4d564e2d89534db0c5194c14129d9f. All 743 workspace tests and the complete disposable-server suite passed, including delegated collection setup, shared chat presets, credential approvals, schema workflows, and full restore/recovery with and without history plus a second-generation restore.

Collection managers can create, update, and delete fixed-destination webhooks and subscribe to their collection's events. These operations require both ManageEventSubscription and ReadAudit. Global sinks require direct collection grants; administrators can grant, list, and revoke them through the CLI. The required pinned integration run covers the delegated lifecycle, administrator chat presets, credential approvals, and full backup/restore recovery.

Breaking (preset arguments): pass chat-provider destination URLs through --destination-url-file PATH; literal destination URL arguments are no longer accepted. Store those files with restrictive permissions. See collection-owned webhooks.

Breaking (server target and backup output): upgrade the server before using collection self-service. Stop every writer and take a PostgreSQL snapshot before the collection-sink migration, then deploy matching v0.0.18 binaries. Recovery requires that snapshot and matching v0.0.17 binaries. New backups use format 8; restore input accepts 6, 7, and 8. Older servers cannot restore format 8. See upgrade and recovery instructions.

CLI v0.0.13: client v0.13.0¶

CLI v0.0.13 pins hubuum_client 0.13.0, which targets Hubuum server v0.0.17. Cargo.toml records that client's server version and the immutable multi-platform image used for CLI integration checks: ghcr.io/hubuum/hubuum-server@sha256:cc0518167816bfddb38853b8b7217c4a347511318d51e1abca93ca418f31b302. The server tag is v0.0.17, source commit 4a03d56b27f35af62175a80d09d36d0d41c4a663. The client's reviewed OpenAPI contract grows from 220 operations and 330 schemas to 227 operations and 336 schemas. The client release evidence records all 87 reconciled wire-model mappings and its own pinned integration, feature, Rust 1.88, contract, and semver checks.

The CLI continues to enable only the client's blocking feature. The client's MSRV is still Rust 1.88; no CLI MSRV is declared or implied by that requirement. This release is verified with Rust 1.99.0. Existing workspace public interfaces are unchanged; the JSONC parser update explicitly retains the existing syntax. The new hubuum-update crate adds a small typed update interface backed by self_update 1.3 (upstream MSRV 1.88), with GitHub, Rustls, tar/ZIP, and checksum features. Chat webhook presets generate ordinary webhook configuration for Slack, Mattermost, and Discord. Sink create/update exposes delivery policies; subscription filter JSON accepts task kinds. Delivery health retains nullable collection IDs for system subscriptions, and delivery records retain purpose and deferral metadata. System-subscription CRUD and notification preview/test have no dedicated CLI commands; use the server API. These limits mean that the CLI does not expose every operation in the upstream OpenAPI contract.

Breaking backup output: new backups use format 7, which older servers cannot restore. Staging accepts formats 6 and 7; keep existing format 6 files intact. Restores reset transient sink scheduling while preserving notification configuration and terminal delivery history. See backup migration.

Breaking server upgrade: stop all API, worker, and restore-executor writers, take a PostgreSQL snapshot, then apply migrations and start matching v0.0.17 binaries. Binary-only rollback is unsupported. Recovery requires that snapshot and matching v0.0.16 binaries, losing subsequent writes. Optional Treetop installations must upgrade to protocol 0.1 and migrate their policy bundles. See the server release notes.

This verifies Linux amd64 from the multi-platform index, not every architecture.

All three webhook presets were created through the CLI and rendered by the real server preview endpoint, including [TEST] messages, Discord length bounds and disabled mentions, and pacing updates/clearing. The test does not resolve real provider secrets or send messages to hosted Slack, Mattermost, or Discord. CLI v0.0.11: client v0.10.1¶

CLI v0.0.11 pins hubuum_client 0.10.1, which targets Hubuum server v0.0.14. Its integration checks pin the immutable server image ghcr.io/hubuum/hubuum-server@sha256:6c1c8d7316a1f60a02e4505611a44e21030ba678b5b451f5b293a12f2bd87594 in Cargo.toml. The client pins the server's 204-operation OpenAPI contract; the previous v0.0.9 target had 202 operations. The added structured-search POST routes have no dedicated CLI commands in this update. Administrative config output includes the newly modeled storage, database-role, secret-source, token-hash, tracing, query-budget, and traversal settings. The OpenAPI contract is unchanged from v0.0.13 apart from the server version. Client 0.10.1 retains the public APIs and features of 0.10.0.

Backup format 5 excludes password hashes, tokens, and token scopes. Restore confirmation queues work for the matching hubuum-admin --restore-executor. Upgrade the server, administrator, and template-worker binaries together and run hubuum-admin --migrate before starting the server when upgrading from an older schema. Server v0.0.14 adds no migration over v0.0.13; update any separately deployed restore executor to obtain its history-free restore fix. Format 4 backups require a compatible older server. Existing history-free format 5 artifacts can be restored by the fixed executor. See migration and recovery.

The CLI continues to enable only the client's blocking feature. Verification uses Rust 1.98.0; this update does not introduce a CLI MSRV declaration. The client's own MSRV remains 1.88, which is not a claim about the complete CLI dependency graph.

The reproducible CLI integration check is cargo build --locked && python3 scripts/test-backup-restore.py. It provisions its own pinned PostgreSQL and Hubuum containers, applies migrations, runs the restore executor, and checks both backup history settings and both restore confirmation modes. Each cycle verifies receipt-only monitoring, terminal success, rejection of the old token, administrator password reset, and recovery of a deleted object with JSON-null data, preserving its revision and timestamps. It then checks default backup staging immediately after a history-free restore and performs a full second-generation restore after further updates and a deletion. CI requires this check before publishing rolling binaries.

Executed on 2026-09-10 with Rust 1.98.0 and Podman 5.8.2 on Linux x86_64 against the immutable image above. Its source revision is 0b0aa17f278496a32cc018cfcac56f34a408ccd6 (server v0.0.14).
